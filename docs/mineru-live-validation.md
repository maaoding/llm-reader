## 等待状态修复

初次上传得到 HTTP 200，应用却在第一次轮询后暂停。随后只读查询显示同一个云端任务已经 `done`。继续分析读取原任务并完成 OCR、问答与归档。

代码核对发现，客户端将 `waiting-file` 与 `failed` 一起作为失败处理。官方标准 API 文档说明，`waiting-file` 还包含上传后等待排队提交解析的状态，因此不能直接报错。已改为继续有界轮询，保留取消、超时以及原任务续跑逻辑；明确的 `failed` 和未知状态仍报错。

本次首次暂停没有记录云端响应正文，不能单凭该次日志还原具体返回状态。`waiting-file` 的误判由代码检查和先失败、后通过的本地回归明确复现。真实 OCR 与问答使用原打包程序续跑已完成的云端任务；修复后的完整等待流程另用本地模拟服务验证，避免为回归再次上传真实文档。

回归覆盖连续两次 `waiting-file` → `pending` → `running` → `converting` → `done`，断言只提交一次、上传一次并缓存结果。Electron 回归还覆盖等待入队期间暂停、重启、复用远端任务完成分析及页码引用。

## 请求隔离与用量

主进程只记录公开域名、操作类别、HTTP 状态、客户端标识、是否有鉴权以及匿名会话分组；不记录密钥、完整认证头、签名 URL 或请求正文。

- 应用请求中，MinerU 创建批次、任务查询使用其 Bearer 凭据；阿里云预签名 PUT 和结果 ZIP 下载均没有附带认证头。
- Go 的 5 个分析请求复用同一分析会话，问答及其规划复用另一个会话。MinerU 和存储请求没有附带 Go 会话头。
- Go 接口返回的分析用量为 10,187 tokens；本轮问答为 2,887 tokens，已含规划的 1,005 tokens。可汇总共 **13,074 tokens**，不含启动时的连接探测，不能视为完整账单。
- MinerU 处理了两页，没有返回货币费用或 token 用量，因此不估算费用。
