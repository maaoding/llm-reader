## 本次结论

- MinerU 云端、SiliconFlow `BAAI/bge-m3`／`BAAI/bge-reranker-v2-m3`、OpenCode Go `deepseek-v4-flash` 均实际调用成功。
- 修复混合检索中关键词独有证据被融合排序挤掉的问题。固定的 24 题中，混合检索关键证据从 **26/27 增至 27/27**，3,000 字缩减预算结果相同。
- 修复模型输入中的合并单元格列位置和多层表头行关系。重复展开的文字仍指向同一真实单元格，裁剪后同步保留正确来源范围；对异常巨大展开增加容量检查。
- 六页数字 PDF 和相同页面的纯扫描 PDF 均完成真实解析、跨页问答及来源检查。主要内容得到保留，特殊 Unicode 字符仍有上游识别损失。

## 长文本对照

`scripts/knowledge-hard-fixture.ts` 固定了一份虚构站点管理手册：12 个章节、308 个原文块、141,677 个 Unicode 字符。包含名称相似的站点、废止规则、数值干扰、必要条件、独立来源、撤回权限、跨章时间限定与无答案问题。材料、问题与预期证据均在运行前编写，不从模型输出反推标准答案。

24 题中，20 题有答案，共 27 项关键原文；4 题无答案，不计入证据召回分母。全部组使用同样的问题、原文和输入预算，不生成章节笔记；取材规划固定走生产代码的本地回退，避免额外规划词与答案标签影响检索比较。向量和重排均为真实服务输出，没有用人工向量模拟效果。

| 检索组 | 修复前 6,000 字 | 修复后 6,000 字 | 修复后 3,000 字 |
| --- | --- | --- | --- |
| SQLite FTS | 26/27 | 26/27 | 26/27 |
| FTS + 向量融合 | 26/27 | **27/27** | **27/27** |
| 扩大候选池、不重排 | 26/27 | **27/27** | **27/27** |
| 扩大候选池 + 重排 | 26/27 | 26/27 | 26/27 |

“扩大候选池”是用于隔离候选数量影响的控制组，不生成回答。重排和扩大候选池组使用同一候选构造路径、最多 60 项候选和 5 秒时限；本次没有重排超时回退。

失败样本与改动依据：

- H01：FTS 未找到废止的旧期限，因此只能回答现行期限；混合检索补到了旧规，答案能明确区分两者。
- H19：原本 FTS 排名第二的“连续自然小时包含夜间与节假日”条款，被共同命中的干扰段落挤到融合排序后方。原融合只保护语义侧独有证据；改为同时保留两侧各自的领先结果后，混合检索保留该条款，Go 能据此解释周末连续计时。
- H19 的重排组仍丢失该条款。完整回答虽给出连续计时的结论，但缺少关键限定的原文支持，不能按“答对数值”算作完全有据。
- H05 重排回答开头出现“不必”，随后却说明仍须追认，属于模型表述自相矛盾。H24 的 FTS 回答正确拒绝默认数值，但把本轮未检索到定义扩大成了对全书的断言。两者保留在失败记录中。

每组三类问答各 24 题，首轮生成 **72 份真实完整回答**。修改后重新取材；53 个输入上下文及问题完全相同，明确复用首轮答案，另 **19 个变化输入重新调用 Go**。复用项已逐项核对整个上下文，排除仅用于显示的重排耗时和规划用量字段；不把缓存复用计作新联网回答。

人工核对主结论、适用条件、是否得到原文支持及拒答。所有组都没有给四道无答案题编造具体数值，但存在上述措辞范围问题。出现的 `[P编号]` 都属于本次原文；首轮 FTS 两题、混合一题只写了裸 `P编号`，没有产生可点击引用，这与“没有伪造编号”分开记录。

前 8 题标为开发题，后 16 题原计划作复核。H19 的失败已用于本次修复，因此这些结果是同批回归，不再声称是独立盲测或具有统计泛化结论。

## 真实复杂 PDF

`scripts/generate-knowledge-hard-pdf.py` 生成两份六页文件。内容包括双栏阅读顺序、旧规干扰、两页续表、合并表头、脚注、公式、恢复清单和 Unicode 字符。扫描版逐页由数字版渲染，已确认没有文字层。六页均实际渲染并查看。

MinerU 云端首次准备耗时：数字版约 **10.7 秒**、扫描版约 **12.1 秒**，均得到 8 个结构节点及 31 个可检索块。原文就绪时章节笔记仍为 0，不需要先支付整书笔记调用才能问答。页眉控制词没有进入检索；所有来源页号位于 1—6。

19 个预设检查点中，两版各 **17/19** 逐字匹配（忽略空白并做 NFC 归一化）。其中一处只丢失句末标点；忽略标点后各 **18/19**。余下是特殊字符行。公式及数值、两个表格的 13 个原始单元格、5 列位置与两个合并单元格均保留；两张续表保留各自真实页码，不臆造合并关系。

表格原来转换成三列表头和五列数据：

```text
组别    普通样本    异常样本
        保留天数    阈值    保留天数    阈值
蓝组    31          0.72    93          0.88
```

修复后按真实覆盖列展开，多层表头仍按行排列。每次出现的单元格文字记录自身的原始范围，已有来源精度不会被提升为不存在的行级页码。供应商用 `td` 表示的视觉表头仍保留原标记，没有根据位置猜测 `th`。

前后各针对两版提出 8 道问题，共 **32 份真实完整回答**，覆盖跨页数值、申诉表注、脚注限制、公式边界、现行／旧规则、无答案与恢复顺序。两轮主结论和数值均正确；修复前 1 条、修复后 2 条未使用方括号引用格式，其余已生成引用均可在本次上下文中验证。此次 PDF 问答使用真实规划，前后规划没有锁定，因此仅作为端到端回归，不据此量化表格修复带来的模型质量增益。

额外通过实际 Electron UI 生成 1 份跨页回答，核对第 3、4 页来源跳转和返回阅读位置，保存含表格来源的归档，并查看明暗主题下 1440×900、940×600 窗口。无横向溢出，来源按钮和输入框可用。

### 特殊字符与测试文件校正

强制 OCR 对两种版式都保留了 `μ`、`Ω`，但丢失 emoji、将 `𠮷` 识别为 `吉`，也丢失组合重音。关闭强制 OCR 的初次对照中，发现本机 PDF 生成库为非 BMP 字符生成了错误的 ToUnicode 映射；该次字符结果不能直接归责于 MinerU。

生成器现已将对应映射修正为 UTF-16BE 代理对，并在生成后用独立 PDF 读取器检查 `μ`、`Ω`、`😀`、`𠮷`、`é` 全部可回读。只改测试生成器，不修改供应商依赖。原文件已保留，修复后的扫描版 SHA-256 与原版完全相同。

对修正后的数字 PDF 再次关闭强制 OCR，真实云端准备约 **9.1 秒**：组合重音保留，但 emoji 与 `𠮷` 仍返回替代字符。因而“关闭 OCR 即可完全保真”不成立；本期继续保留原 PDF 页面供核对，没有凭猜测回填字符。脚注没有供应商明确关联时，仍展示“缺少明确关联”诊断。

旧 PDF 缓存不会在升级时被自动改写。要采用新的表格表示，用户可点击“重新准备原文”，在可用时复用本地原始解析产物，随后相关笔记和向量需重建；既有归档引用快照保留。混合检索的证据保护立即生效，不需要重建向量。

## 复现与证据

源码脚本不含凭据。联网运行须使用已获授权、已保存的加密模型配置；读取默认应用配置，或通过 `LLM_READER_REAL_API_SOURCE_USER_DATA` 指定 Go 配置目录。Embedding、重排、文档凭据可分别通过 `LLM_READER_EVAL_EMBEDDING_SOURCE_USER_DATA`、`LLM_READER_EVAL_RERANK_SOURCE_USER_DATA`、`LLM_READER_EVAL_DOCUMENT_SOURCE_USER_DATA` 指定，默认为同一应用目录；要求相同系统加密上下文。只复制所需配置，不复制个人书籍。

密钥在 Electron 主进程解密和发出；不返回给 Renderer、外层评测脚本或日志。资料只发往本次明确核对的 Go、SiliconFlow 和 MinerU 地址；云端签名资源由生产代码限制来源，并避免附带供应商认证。

```powershell
pnpm run build:electron
node scripts/knowledge-hard-eval.mjs baseline
node scripts/knowledge-hard-eval.mjs optimized
python scripts/generate-knowledge-hard-pdf.py
node scripts/knowledge-pdf-live.mjs
node scripts/knowledge-pdf-answers.mjs baseline
node scripts/knowledge-pdf-answers.mjs optimized
node scripts/knowledge-ui-live.mjs
```

基线须在修改前源码上运行；标签不会自动切换 Git 版本。脚本逐题保存断点，成功的真实向量／重排响应可复用。PDF 生成使用既有 Windows 字体和 Poppler，可通过 `LLM_READER_PDFTOPPM` 指定后者，不自动安装依赖。关闭强制 OCR 的修正文件复验使用 `knowledge-pdf-live.mjs --text-layer --fixed-cmap`。

本机证据在 `output/knowledge-hard-20260909/`：`baseline.json`、`optimized.json`、`review.json`、各次网络记录、`pdf-live.json`、各版原始解析与结构、`pdf-quality.json`、前后 PDF 回答、`ui-live.json` 及四张主题截图。文件包含自写材料与生成回答；加密测试配置独立留在 `tmp/knowledge-hard-*`，不进入源码提交。文档定位可复核，不把命中编号或 HTTP 200 等同于答案正确。
