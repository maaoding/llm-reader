## 功能与兼容性检查

- 自动检测需要标题与列表/强调等组合，或闭合代码围栏、有效表格等结构证据；有歧义时保持纯文本，当前书籍可手动指定。模式仅保存在本机当前书籍的展示偏好中。
- 使用带原始位置的 Markdown 语法树，通过允许的 DOM 节点渲染；HTML 按文字显示，链接和图片不获得导航或网络加载权限。超出 2,000,000 个 UTF-16 代码单元、50,000 个语法节点或 64 层结构，以及无法完整映射的内容回退基本阅读。
- 原始文件、原文准备、索引及来源坐标保持原有契约。正文可见搜索与跨强调/代码的划词映射到原始 TXT 的 Unicode 码点；模式切换和重启保留摘录、引用、来源与阅读位置。书名继续根据原始 TXT 推断，与展示模式无关。
- 新增单元检查覆盖保守识别、安全节点、嵌套列表、引用、代码、表格、Emoji、转义、实体、原文位置、旧锚点、独立书籍偏好、过深结构回退和模式无关的书名推断。
- 新增桌面检查覆盖 1180×800 与 940×600、浅/深色、100%/125% 界面缩放，以及显示模式、恢复默认、跨格式选区、实际问答 IPC、引用点击、归档、摘录、搜索和重启恢复。模型回答为本机固定模拟，验证功能链路，不计真实服务质量得分。

补充复核先后发现引用块中的多行 HTML 文字会错误回退，以及按 Markdown 块推断书名会把前置分隔线当成标题；对应复现用例在修复前失败、修复后通过。早期日志和中间回归保留在本机忽略目录，最终候选另跑完整验证。

长文本复核另确认旧表格识别正则在大量 `|` 的长行上出现平方级退化，已改为逐行结构判断。`detection-performance.json` 保留单行合成压力记录：旧正则在 16,000 字符样本约 68 毫秒，新生产检测函数处理 1,800,000 字符样本约 0.73 毫秒。这只验证该检测场景，不代表整本书排版性能；同一大文本也进入单元回归。

本机记录目录为 `output/release-v1.3.0-20261025/`。`final-candidate-inputs.json` 保存源码、测试、锁文件和构建配置的摘要；最终完整验证结束时再次核对这些输入未发生变化。

## 交付边界

本轮安装验收只使用一次性 GitHub-hosted Windows runner，未读写日常书库。真实模型或 PDF 服务质量没有重新评分，历史固定 12 题的 11 题完整、I11 部分完成记录保持原样。运行时依赖审计 `pnpm audit --prod --json` 退出码 0、公告 0；该结果不表示完整开发依赖审计已执行。

NSIS 全新安装/覆盖升级使用[现有 Windows 验收工作流](../../.github/workflows/windows-package-validation.yml)。[安装验收脚本](../../scripts/validate-windows-package.mjs)显式限定一次性 GitHub-hosted Windows runner，本轮不在日常使用的电脑上运行该脚本。源码 E2E、解包程序回归、NSIS 安装升级与真实服务质量分别记录。公开状态以 [GitHub Release](https://github.com/maaoding/llm-reader/releases/tag/v1.3.0) 为准，官网只在 Release 公开后同步。

发布阶段把安装验收的公开基线推进至 v1.2.0，固定安装器大小和 GitHub Release 公布的 SHA-256，并在已安装程序回归中加入本轮 Markdown 与取材用例。应用源码、依赖和打包配置沿用上述已测候选；这两项安装验收入口的变更另行静态检查并由云端实际执行。
